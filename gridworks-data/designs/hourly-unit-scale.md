# hourly-unit-scale

Status: Draft · Pass 0 · Updated 2026-10-26 · Linear: OPS-630

**EDD: no** build-out in gridworks-data, verified by the two hourly
functions run on `tsdb_tap` over Maple's window with `hp_kwh_th`
populated for every hour that has flow and temperatures, then the same
script on prod and a refresh of `cached_hourly_data`.

> What this is: the journal DB's hourly functions stop selecting readings
> by a unit literal and read each channel's scale from a table generated
> from the sema snapshot, so a derived channel recorded in one unit enum
> and a measured channel recorded in another read as the same quantity.

## The fault

`gridworks.calc_energy_1hr` and `gridworks.calc_hourly_data` (source:
gridworks-data `src/gw_data/db/scripts/misc/create_udf_*.sql`) pick
readings with `channel_name = '...' AND unit = '...'`, one literal per
channel. The journal records a DataChannel's unit in
`spaceheat.telemetry.name` (`GpmTimes100`) and a DerivedChannel's in
`gw1.unit` (`GpmX100`). Maple's `primary-flow` is the fleet's one derived
flow channel, so its hourly `hp_kwh_th` came out empty (OPS-608). Oak's
`sieg-send-flow` was in the same enum until 2026-10-23. Any derived
channel that stands in for a measured one meets the same literal.

On 2026-10-26 the production `calc_energy_1hr` was edited in place to
`unit IN ('GpmTimes100', 'GpmX100')` for primary-flow. The repo file has
the single literal; nothing else differs. The journal-DB rule is one SQL
script in gridworks-data, tried on `tsdb_tap`, then run on prod, so step
1 below is the repo catching up with what is deployed.

## The table

`gridworks.unit_scale`, one row per `(unit_type, unit)` the journal can
hold: the quantity (from `gw1.unit.quantity.projection` and
`gw1.telemetry.name.quantity.projection`) and the scale from the stored
integer to the engineering unit the hourly columns use (gpm, °C, W,
$/MWh). Generated by a script in gridworks-data from the vendored sema
snapshot, so the rows are a projection of the vocabulary and the script
is the only writer. A unit the snapshot names and the table lacks is a
generation fault, caught by a test that every `unit` in
`reading_channels` resolves.

The hourly functions join `reading_channels` to `unit_scale` on
`(unit_type, unit)` and select by `channel_name` and quantity:
`primary_flow_gpm` is the average of `value * scale` where the channel is
`primary-flow` and the quantity is FlowRate. Every unit literal in both
functions goes, not just the flow ones.

## Plan

1. A script under `misc/` that makes the repo's `calc_energy_1hr` the
   deployed body (the `IN` form), so the repo states what runs.
2. The generator and `unit_scale`, with its test.
3. Both functions rewritten to the join; tried on `tsdb_tap` against
   Maple's window and one house per layout family; then prod, and a
   refresh of `cached_hourly_data`.

Out of scope: the web-backend's `readings_units.py`, which already
scales both spellings in code; the realtime seam's unit-less reading,
which is OPS-622's.

## Open

- Whether `unit_scale` is a table or a view over a JSON document the
  generator writes; a table is simpler to join and to test.
- The scale for a quantity is in neither projection word; it is in the
  enum value's name by convention (`X100`, `Times100`, `Times1000`). The
  generator derives it from the name until a sema word states it, which
  is a sema question with the spec first.
