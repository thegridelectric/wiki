# The simulated plant

Status: Draft · Pass 0 · Updated 2026-11-12

> What this is: the simulated terminal asset as built: one process,
> `ta-plant`, that reads a house's hardware layout, runs the physics of
> its heating plant from a compiled Modelica model, and exchanges two
> words with that house's scada. A first draft written from the code and
> the pull request descriptions (gridworks-terminalasset PRs 3 to 6,
> branch `ow/beech-plant`, not yet on `dev`). The Modelica files were
> outlined and not read line by line. Sections marked **Question** are
> for the plant's author to answer or correct.

## The parts

| Part | File | What it is |
|---|---|---|
| The actor | `src/gwta/plant.py` | `SimulatedPlant`, a terminal asset GNode on gridworks-base. Owns the broker connection, the flux timer and the model |
| The layout read | `src/gwta/plant_layout.py` | Decodes the layout through the sema snapshot into a `PlantLayout`: the terminal asset's GNode, the scada's alias, the channels simulated devices capture, the relays and their control configs, the hydronic section |
| The model seam | `src/gwta/plant_model.py` | `PlantModel`: time and actuations in, channel values out, no knowledge of the broker. `DriftModel` is a seeded random walk per channel that ignores actuations |
| The physics model | `src/gwta/fmu_model.py` | `FmuPlantModel`: steps an FMI 2.0 co-simulation FMU with `fmpy`, writes relay positions to its inputs, reads its outputs into channel values |
| Family adapters | `src/gwta/house0.py`, `src/gwta/katahdin.py` | For one layout family: which FMU output each channel reads and which FMU input each relay drives |
| Sensing | `src/gwta/sensing.py` | What a sensing device makes of a plant value: a tank thermistor's microvolts, a flow meter's pulse rate |
| The Modelica source | `modelica/` | `Hydronic.mo`, a library of parts; one top model per plant |
| The build | `Dockerfile`, `modelica/build_fmu.mos`, `scripts/build_fmu.sh` | OpenModelica 1.27.1 compiles the models to FMUs in a build stage. The FMUs are never committed |

## What crosses the broker

Two words, each wrapped in a `gw` envelope on `amq.topic`, aliases with
their dots as hyphens:

- **`sim.plant.flux`**, plant to scada, routing key
  `gw.<plant>.to.<scada>.sim-plant-flux`. A value for every enabled
  channel a simulated sensing device captures, in the channel's own
  encoding, every `--flux-seconds` (default 5).
- **`sim.plant.actuation`**, scada to plant, routing key
  `gw.<scada>.to.<plant>.sim-plant-actuation`. A relay's node name and
  whether it was energised or de-energised.

The plant sends `gw` messages because that is what the scada
evaluates. Channel names and relay node names are all that cross. A relay's state
name and a 0-10 V level are never sent. An actuation that fails to
decode, or names a relay the layout does not have, is logged and
dropped.

Both stamps on a flux are wall time. The clock is injected, so a
coordinator's timesteps can replace it.

OPS-672 changes the steady flux to one that reports a channel when it
changes.

## Start

1. Decode the layout. It is a `gw.house0.layout`, a `gw.house0.no.sieg`
   or a `gw.katahdin.layout`, and the adapter is chosen by which word it
   is.
2. Refuse to start unless `GWTA_SERVICE_ALIAS` equals the alias of the
   layout's TerminalAsset GNode.
3. Write the identity file from that GNode if none exists.
4. With `--fmu`, build an `FmuPlantModel`; without it, a `DriftModel`.
   A `gw.house0.no.sieg` has no FMU.
5. Bind the actuation key and start the flux timer.

Each of these refuses at start with a message naming the cause: a
channel with no FMU output, a named output the FMU lacks, a relay the
model needs whose control config does not say which state is energised,
an override naming no parameter of the FMU, a zone or tank count that
differs from the FMU's.

## How a layout becomes a running model

The adapter builds two tables from the layout.

**Channels to outputs.** A fixed table gives the family's standard
channels (`hp-lwt` → `hpLwt`, `dist-flow` → `distFlow`). Tank depth,
zone temperature and zone whitewire channels are generated by looping
over the layout's store and its zone call circuits
(`tank2-depth1` → `tankDepth[2,1]`, the zone at circuit position i →
`zoneTemperature[i]`).

**Relays to inputs.** Each relay the model has a part for drives one FMU
input. The value for each of the relay's two states is keyed on the
state names in the relay's `relay.control.config`, and the layout says
which state is the energised one. For a House0 house:

| Relay | FMU input | Meaning of 1 |
|---|---|---|
| `hp-scada-ops-relay` | `hpEnable` | contact closed |
| the backup's failsafe relay (`hp-failsafe-relay`) | `hpScadaControl` | the scada has the heat pump's call |
| `primary-pump-failsafe-relay` | `primaryPumpScadaControl` | the scada runs the primary pump |
| `primary-pump-scada-ops-relay` | `primaryPumpOn` | contact closed |
| `hp-loop-on-off-relay` | `siegMotorOn` | valve motor running |
| `hp-loop-keep-send-relay` | `siegTowardKeep` | moving toward keep (`SendLess`) |
| `charge-discharge-relay` | `chargeDischarge` | charging the store |
| `store-pump-relay` | `storePumpOn` | contact closed |
| the backup's aquastat control relay (`aquastat-ctrl-relay`) | `boilerScadaControl` | the scada has the boiler |
| each zone's failsafe relay | `zoneScadaControl[i]` | the scada has the zone's call |
| each zone's ops relay | `zoneScadaCall[i]` | contact closed |

`vdc-relay` and `tstat-common-relay` are heard and switch nothing in the
model.

The two places a House0 relay hands a decision to the plant's own
hardware are in the model. With every relay de-energised, an aquastat on
the buffer fires the boiler and the heat pump is not called.

**Units.** The FMU works in SI units. Each output is encoded by its unit
and the channel's telemetry name: kelvin to `WaterTempCTimes1000`, cubic
metres per second to `GpmTimes100`, watts to `PowerW`. A channel whose
value is a device's own reading goes through `sensing.py` first.

**Stepping.** `advance_to` moves the model to the wall-clock instant of
each flux, in pieces of at most 5 seconds (`MAX_FMU_STEP_S`), because an
OpenModelica FMU looks for its own events only at the end of a step. An
actuation sets its input at once and the model sees it on the next
advance.

## The models

| Model | File | Built to | Plant |
|---|---|---|---|
| `Katahdin.Plant` | `Katahdin.mo` | `KatahdinPlant.fmu` | Monobloc heat pump on glycol, plate exchanger, three store tanks, valves V1 to V5, four zones, boiler. One flat equation model with no library behind it |
| `KatahdinComponents.Plant` | `KatahdinComponents.mo` | checked only | The same plant as connected `Hydronic` parts with a placed diagram |
| `Beech.Plant` | `Beech.mo` | `BeechPlant.fmu` | A House0 plant: split heat pump behind a Siegenthaler valve, buffer, three store tanks, oil boiler, two zones, built of `Hydronic` parts and placed as on the plant's schematic |

What the physics does:

- **Water moves where valves and pumps send it.** The pipework is a
  pressure network solved at every instant, so a flow splits by
  resistance, reverses through the store when the house draws more than
  the source gives, and stops when a pump has nowhere to send it.
- **Heat follows the water.** Each tank is nine layers that keep their
  stratification, with depth sensors on layers 2, 5 and 8. The heat
  pump's capacity and COP are tables over outdoor and leaving
  temperature. Each zone is a thermostat with a deadband, an emitter and
  a room that loses heat outdoors.

What it leaves out or fixes:

- Every coefficient is a placeholder: pipe resistances, pump curves,
  conductances, the heat pump tables, the buffer's volume.
  `--fmu-overrides` replaces any parameter at start.
- Outdoor temperature is a fixed input.
- No 0-10 V level reaches the plant, so every pump runs at full speed.
- No defrost. The compressor has no minimum off time and short-cycles
  when the store reaches the leaving-water limit.
- Katahdin: no immersion elements, and the boiler is a volume of water.

Each FMU is a co-simulation FMU with its own CVODE solver, so a step's
accuracy does not depend on its length. Its binary is for Linux on the
processor the build ran on.

## A model is per house shape

The Python adapter serves any layout of its family. The FMU does not.
`Beech.Plant` has `constant Integer nZones = 2` and three store tanks,
and those sizes are fixed when the FMU is compiled. The adapter counts
the FMU's zone and tank outputs and refuses a layout that differs.

A house with another zone count needs its own top model, built of the
`Hydronic` parts, and a rebuilt image.

## How it is checked

- **In `ci.sh`:** ruff, pyright, the FMU build in Docker, then pytest.
  `tests/test_house0.py` has 18 tests, 12 against the FMU;
  `tests/test_katahdin.py` covers the Katahdin adapter.
- **In the image build:** `check_components.mos` checks that
  `KatahdinComponents.Plant` and `Beech.Plant` translate with equations
  and unknowns in balance.
- **By hand:** an FMU of `KatahdinComponents.Plant` stays within
  0.0025 K of the flat model over two simulated days. An FMU of
  `Beech.Plant`, driven through each operating mode, has flows in the
  schematic's directions and an energy balance that closes.
- **By experiment:** a whole scada ran the Beech plant in containers for
  thirteen and a half hours and the plant heard 2593 actuations across
  all 15 relays, with all 50 plant-fed channels moving
  (`experiments/2026-11-11-beech-sim-compose/`).

## Questions

**One model per layout word.** The aim is one FMU for each layout
word (`gw.house0.layout`, `gw.house0.no.sieg`, `gw.katahdin.layout`),
which runs any house of that word from its layout and its operational
params. Today `Beech.Plant` has Beech's zone and tank counts compiled
in. What is the route from here: a model compiled for the largest zone
and tank counts with the unused ones switched off by parameters set at
load, a top model generated from the layout at build time, or something
else? What in `Beech.Plant` is Beech's alone and what is any House0
house's?

**Zone structure.** A zone call circuit in the layout is more than a
count: the zone it serves, its emitter type (`RadiantSlab` with a floor
temperature channel, `FanCoil` which may cool, `Other`), its thermostat
kind and its setpoint source. The model's zones are identical: one
thermostat with a deadband, one emitter and one room each, with the same
parameters. The zone model is being worked out under OPS-532 (a zone
is the thermal space, a circuit is the chain from wall stat to actuator,
and a room can have two circuits), and the plant's zone part follows the
layout word as it settles. What does a
zone slot in the model need so one compiled model covers a slab zone, a
fan coil zone and two circuits serving one room?

**Coefficients.** Every one is a placeholder. Where do real values come
from: the layout, the house's operational params, a per-house overrides
file, fitting against the house's journal data? Which of them matter to
control behaviour and which do not?

**The two Katahdin models.** The FMU is built from the flat model while
the component model is only checked. Which one stays?

**Step length.** The model advances in pieces of at most 5 seconds. What
limits a one-second or shorter step, which OPS-672 needs for power: the
solver's cost per step, or nothing?

**0-10 V and outdoor temperature.** What should send a pump speed to the
plant: a field on `sim.plant.actuation`, or a second word? Where should
outdoor temperature come from: the weather service's forecast for the
house, or a scripted trace?

**A Katahdin layout.** The repo makes a `gw.katahdin.layout` from a
House0 layout (`ta-katahdin-layout`). Layouts otherwise come from
tlayouts. That tool moves there or goes, and the Katahdin fixture is
made in tlayouts.

**`gw.house0.no.sieg`.** It has no FMU. Is that a third top model built
of the same parts?

**Fidelity.** How close does the plant need to be for the tests it
exists for? The first purpose is comms and control testing, where
plausible dynamics are enough. Is there a second purpose (control
tuning, FLO validation) that needs a plant fitted to a real house, and
what check would show it is close enough?
