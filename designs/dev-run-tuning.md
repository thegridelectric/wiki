# Tuning a dev run

Status: Draft · Pass 0 · Updated 2026-11-25 · Linear: OPS-722

**EDD: no** tooling for experiments, verified by one simulated-stack run
whose houses, params and signals were set through it and whose journal
shows the settings took.

> What this is: the open questions for a surface that sets what a dev
> universe runs with: each simulated house's hardware layout and
> operational params, and later the weather and price signals a run sees.
> Whether it is a terminal tool or a web page is one of the questions. It
> starts after OPS-720 settles d1 identity, because the knobs here are the
> inputs that design leaves to the generators.

## Why

A dev run today is set by hand in several places. The simulated stack's
houses are generated by `gen_layout.sh` from a pinned tlayouts commit; the
two houses differ by a constant in the generator and the web server's
`Serve` flag is set by editing the layout after generation. FLO tuning and
the operator hold live in each house's `operational-params.json`. The
weather and price services read live sources (NWS, ISO-NE day-ahead at the
pricing node) through their own settings; a run cannot ask for a cold
week or a price spike. Comparing two variants of one house means editing
files and rerunning the stack, and nothing records what a run was set to.

The hundred homes set this year's requirements. Reproducing a field
behaviour in a dev universe, then trying a change against it, is how
those requirements get tested without a house.

## Questions

1. **What is the knob set?** The per-house override slot OPS-720 leaves
   open is the first half: what a `simulate(config, ltn_alias, ops)` call
   takes beyond the house spec. The FLO tuning and the operator hold
   differ between spruce and beech today. The slot should stay small, and
   this surface is its first consumer, so this design sizes it.
2. **Inputs or outputs?** A surface that edits a generated layout
   recreates the drift OPS-720 removes. The proposal is that it edits
   only generator inputs and regenerates, and that the `Serve` flag gets
   a config field so no post-edit remains.
3. **Textual or web?** A dev universe runs on a laptop or a pod and its
   config is files pinned by commit, so a terminal tool over those files
   fits first. A web page earns its place when a shared sim box has
   several people tuning one run. The proposal is a CLI in tlayouts first,
   with the web page a later spoke that calls the same functions.
4. **Boot-time or live?** A layout is read at scada boot. Operational
   params have a word (`gw.operational.params`) and a live path to a
   running scada. Which knobs may change mid-run, and whether the surface
   uses the live path or restarts the house, decides what the tool is.
5. **Where is a run's setting recorded?** Universes are durable and runs
   are ephemeral, so a run's settings are a per-run record. Whether that
   is a file in the experiment folder, a sema word journaled at run start,
   or both, decides how a run is reproduced later.
6. **What are weather and price as knobs?** The services publish
   forecasts from live sources. A tuned run wants a feed it can replay: a
   recorded week, a shifted week, a synthetic spike. Whether that is a
   replay mode in each service, a sim source behind the same word, or a
   separate feed author, is its own half of this design and comes after
   the house half.
7. **Who else uses it?** If a teammate sets up a run to reproduce a field
   fault, the surface has to say what it set in words the fleet uses.

## What exists today

- `experiments/dev-sim/`: `run.sh`, `pod.yaml`, `gen_layout.sh`, two
  houses (`house/`, `house-buffer/`) and `sources.txt` pinning every repo.
- tlayouts: the House0 generator and the sim drivers; after OPS-720 leg
  2, `simulate(config, ltn_alias, ops)` and `sim_gen.py <house>`.
- `flo_matrix.py` in dev-sim reads a house's `FloTuning` from its
  operational params: one existing reader of the knob set.
- The weather service's forecast carries a fidelity marker (live, stored,
  seasonal.template), a seam a replay source could use.

## Depends on

OPS-720 legs 2 and 4: the override slot, the regen test and the stack
reading tlayouts output at a pinned commit. The house half of this design
starts when those merge.
